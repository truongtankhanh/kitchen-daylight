# API outline (v3, restaurant business app)

Status: **draft for review** (2026-10-27). v3 follows [ADR-0009](adr/0009-owner-business-pivot.md) and [data model v5](data-model.md): the API of the owner's own restaurant (branches, menu, orders, reservations, loyalty, staff operations), replacing v2, which served a directory of third-party venues. Decisions it builds on: [ADR-0001](adr/0001-tech-stack.md), [ADR-0003](adr/0003-authentication.md), [ADR-0007](adr/0007-realtime-sync.md), [ADR-0008](adr/0008-open-items-resolution.md) (the auth, realtime and email parts still hold), and the working assumptions `WA#` of ADR-0009. This is the endpoint inventory and conventions, not the contract; the contract is the generated OpenAPI document (see "Contract workflow").

**Revision of 2026-10-30 (gaps of the admin web design folded in).** The API and data gaps that the admin web design found ([designs/web/brief.md](../designs/web/brief.md), section "API and data gaps found", and the decisions the owner accepted there, [docs/admin-shell-design.md](admin-shell-design.md) included) are folded into this outline as **proposals until the owner confirms them**. What changed: new endpoints (dashboard, `nav-counts`, order items, contact reveal, menu usage and reorder calls, tags and amenities admin, branch delete and zone check, review reply delete, report decision shape, reservation reveal and table change, voucher redemptions and assignments, banner order, points ledger, export read, email suppressions, invoice detail and replace); new parameters (`branchIds[]` on every list and count, filters, cursor paging both ways with `estimatedTotal`, mandatory date ranges with limits); phase changes (`POST /admin/orders` and the revenue read endpoint move to phase 1); new error codes and field-level codes; new realtime events and payloads; new and extended response shapes; new screen coverage rows and open items. Every addition carries a `(brief ID)` tag pointing at the gap row in `designs/web/brief.md`. Columns, tables and constraints of the same gaps are left to [data-model.md](data-model.md). Where the owner or the accountant must still decide, the point is in "Open items", not decided here.

**Revision of 2026-11-03 (gaps of the customer app folded in).** The API gaps that the customer mobile app design found ([designs/mobile/brief.md](../designs/mobile/brief.md), section "API and data gaps found", G1 to G146) are folded into this outline as **proposals until the owner and the engineers confirm them**; the owner approved the fold on 2026-11-03. What changed: one new endpoint (`POST /me/vouchers`, phase 2); new parameters (`scope` and cursor paging on `GET /me/orders`; `scope` on `GET /me/reservations`; `rating` and paging on branch reviews; `excludeTagIds[]`, `verifiedOnly`, `maxPrice` and `suggest` on `GET /menu/search`; `branchId` on `GET /tags`, `GET /me/favorites` and `GET /me/vouchers`; `limit` and `cursor` on `GET /branches`); new fields in `GET /home`, `GET /meta/config`, `BranchSummary`, `MenuItem`, `Quote`, `Order` and `GET /me`; new shapes (customer order list row, reorder draft, reservation slots, own reservation, points ledger); new codes (`DUPLICATE_REPORT`, `IDEMPOTENCY_CONFLICT`, `DUPLICATE_RESERVATION`, four reservation field-level codes) and extra members on `BRANCH_CLOSED`, `ITEM_UNAVAILABLE`, `PRICE_CHANGED`, `OPTION_INVALID`, `ORDER_NOT_REVIEWABLE` and `HAS_ACTIVE_ORDERS`; realtime payload notes; a screen coverage table for the mobile screens. Every addition carries a `(mobile G#)` tag; the prefix "mobile" is used because the web brief has its own G1 to G8, tagged `(brief G#)`. Wording fix: `reorder` is the last **completed** order, not the last order (mobile finding 2, G121). Gaps that depend on an open question of the mobile brief (separate menus per branch, bank details, featured dishes, the voucher flag and so on) are not decided here; the API points among them are Open items 27 to 31. Columns, tables and constraints of the same gaps are left to [data-model.md](data-model.md). Where each gap went: [designs/mobile/gaps-coverage.md](../designs/mobile/gaps-coverage.md) (written afterwards).

**Phase** column: 1, 2 or 3 as in ADR-0009. **Who**: `public` = no token; `customer` = any signed-in user; `staff` = `STAFF`, `MANAGER` or `ADMIN`, **limited to their own branches**; `manager` = `MANAGER` or `ADMIN`, own branches; `admin` = `ADMIN` only (all branches).

## Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1`. Same host as the admin SPA (ADR-0004). |
| Format | JSON, `camelCase` keys. IDs are UUID strings (official codes for `provinces` and `wards`). |
| Money | Integer VND. The **server recomputes every price**; client-sent prices are only compared with the server result (`PRICE_CHANGED`). |
| Images | Full CDN URLs plus `blurhash` and `alt`; never raw keys. |
| Auth | `Authorization: Bearer <accessToken>`. Deny by default; public routes are explicitly marked. |
| Branch scoping | Every staff, manager, order, reservation, stock and report endpoint is filtered by the caller's `staff_branches`; an id outside them returns `404`, not `403` (nothing leaks). `admin` sees all. Every list and count endpoint takes `branchIds[]` (several branches, for the admin branch switcher); with no parameter it uses all the caller's branches, and an id outside them is `404` (brief Z5, A29). Actions on one branch keep the path id or `branchId`. The selection lives in the browser (URL query and `localStorage`); nothing is stored on the server and it is not synced between devices (brief Z6). |
| Revenue visibility | Dashboard revenue, the 7-day table, `/admin/reports/*`, any sum over orders and every `/admin/exports*` call are for `manager` and `admin`; `STAFF` get `FORBIDDEN` there and the dashboard omits the revenue fields for them entirely (absent, not null). `STAFF` still see each order's own total and payment state (brief D4, F1). |
| Locale | `Accept-Language` (`vi` default); translated fields fall back to `vi`. |
| Phone numbers | The API accepts a Vietnamese mobile number in its national form or in international form and stores E.164; anything else returns `VALIDATION_FAILED` with `errors[].code = INVALID_PHONE`. The same rule applies to `PATCH /me`, the phone of an order and the contact phone of a reservation (mobile G97). |
| Customer app: offline copies and addresses | `GET /home` and `GET /branches/{id}/menu` carry no `generatedAt`; the app records the time at which it stored a response and shows it as "saved at"; no API change (mobile G7). There is no address search or reverse geocoding for customers: an address is a map pin plus a province and a ward chosen from `/provinces` and `/wards`; `/admin/geocode` is for staff and phase 2 (mobile G48). |
| Client headers | `X-Client` (`mobile-ios` \| `mobile-android` \| `admin-web`), `X-App-Version`. |
| Errors | `application/problem+json` (RFC 9457 shape): `type`, `title`, `status`, `detail`, stable `code` (catalogue below), `errors[]` (`{field, code, message}`). Some codes carry extra members (see "Payloads added to existing codes"). |
| Pagination | `page` and `pageSize` (default 20, max 50), response `items`, `page`, `pageSize`, `total`. Unbounded tables (audit log, order list by date range) may use cursor paging: `cursor`, `limit`, `nextCursor`, mandatory date range. Cursor lists (orders, audit log, reviews) also take `limit` up to 50 (default 20; reviews 20, 50 or 100), return `nextCursor` and `prevCursor` for paging back (brief A31, V10), and return `estimatedTotal { value, capped }` capped at 1.000 from a bounded count (brief A32, G9); a malformed cursor returns `VALIDATION_FAILED` with `errors[].code = INVALID_CURSOR` (400; brief H4). The date range has a maximum: orders 92 days (a setting, provisional), reviews, audit log and reports 366 days, otherwise `VALIDATION_FAILED` with `RANGE_TOO_WIDE` or `RANGE_INVALID`; order dates filter on `placed_at` in Vietnam time (brief A34, V10, J15). Searchable selects in the admin send `q`, `limit` (max 20) and `ids[]` to rebuild chips of chosen records (brief B2, H3). |
| Idempotency | `POST /orders` and `POST /reservations` require an `Idempotency-Key` header; a repeat with the same key returns the original result (`200` with the same body), never a second record. `PUT`/`DELETE` on favorites are idempotent (`204`). `POST /admin/orders` and `POST /admin/users/{id}/points` take the same header (brief A4, M20). A repeated `POST /admin/orders/{id}/transition` that the same user already applied returns the current order instead of an error (brief A27). The same `Idempotency-Key` sent with a different body returns `409 IDEMPOTENCY_CONFLICT`; the app renews the key whenever the body changes (mobile G57, proposal). |
| Optimistic concurrency | Editable records carry `rowVersion`; a stale `PATCH` returns `409 STALE_VERSION`. Order and reservation transitions also take `rowVersion`, so two staff cannot both act on the same state. `STALE_VERSION` carries `current { rowVersion, updatedBy { id, name }, updatedAt }` (for settings also the current `value`) so the screen can say who changed the record and offer `Xem thay đổi`, `Tải lại`, `Ghi đè` (brief B1, C10, L1, V15). |
| Ownership | The acting user always comes from the token. A customer sees only their own orders, reservations, addresses, points. |
| Privacy | `lat`/`lng` are query parameters of the current request, not stored; logs round or drop them. Staff screens mask customer phone and address in lists and exports by default. Full contact is returned only by a `reveal-contact` call (orders, reservations, users), which writes an `audit_logs` row; the GET endpoints always return the masked version (brief A16, P4, E13). |
| Rate limits | Strict on `/auth/*`; order creation, voucher validation and reservation creation have their own per-user limits (`ordering` settings); lenient on menu reads. `429` carries `Retry-After`. Staff login is limited by an in-process limiter on `/admin/auth/*` plus a per-account counter in Postgres; with more than one API instance the limit moves to AWS WAF or Redis; the figures are open (brief E16). Heavy reports have a stricter limit and a short cache by range and branch (brief J103); at most two concurrent export jobs per user (brief J6); resending an invitation or a staff email is limited to once per 60 s per person (brief E10, K5). |
| Maintenance | `maintenance` blocks customer-facing paths only; `/admin/auth/*` and the admin API stay open so that an admin can switch it off. `MAINTENANCE` on an admin call only means that the server is under technical maintenance (brief L13, E18, D5; not yet confirmed by the owner, see Open items). |
| Versioning | Additive changes only within `v1`; `GET /meta/config` returns `minAppVersion` (per platform, brief L12) for the forced-update screen. |

### Error code catalogue (stable)

Unchanged from v2: `VALIDATION_FAILED`, `CODE_INVALID`, `UNAUTHENTICATED`, `TOKEN_EXPIRED`, `INVALID_CREDENTIALS`, `FORBIDDEN`, `EMAIL_NOT_VERIFIED`, `ACCOUNT_SUSPENDED`, `NOT_FOUND`, `STALE_VERSION`, `ALREADY_EXISTS`, `IN_USE`, `UPGRADE_REQUIRED`, `RATE_LIMITED`, `MAINTENANCE`, `LAST_ADMIN`, `SELF_CHANGE`, `REVIEW_EXISTS`. New:

| Status | `code` | When |
|---|---|---|
| 409 | `BRANCH_CLOSED` | Branch closed, past its order cutoff, or the chosen service (pickup, delivery) is off or outside its hours; carries `reason` and `nextOpenAt` (see "Payloads added to existing codes"; mobile G43) |
| 409 | `ITEM_UNAVAILABLE` | An item is unavailable or its stock is below the requested quantity; carries `items[]` with what is available |
| 409 | `PRICE_CHANGED` | The server total differs from the client's `expectedTotal`; the body is a fresh quote so the app can ask the customer to confirm |
| 409 | `OPTION_INVALID` | Option selection breaks a group's min or max, or an option is inactive |
| 422 | `OUT_OF_ZONE` | Delivery address outside every active zone of the branch |
| 422 | `BELOW_MIN_ORDER` | Subtotal under the zone's or branch's minimum; carries the minimum |
| 422 | `PHONE_REQUIRED` | The customer has no phone number on the profile or the order |
| 409 | `VOUCHER_INVALID` | Unknown, expired, used up, wrong branch or service, below minimum; one code for all so codes cannot be probed |
| 409 | `INSUFFICIENT_POINTS` | Points redeemed exceed the balance or the rules |
| 409 | `INVALID_TRANSITION` | Order or reservation status change outside the allowed flow, or from a final state |
| 409 | `ORDER_NOT_CANCELLABLE` | Customer cancel after staff accepted (they must call or ask staff) |
| 409 | `PAYMENT_NOT_CONFIRMED` | Completing an order whose payment staff have not confirmed (send `confirmPayment` in the same call, or confirm first) |
| 409 | `ORDER_NOT_REVIEWABLE` | Review of an order that is not `COMPLETED`, not the caller's, or older than `ordering.review_window_days` |
| 409 | `SLOT_UNAVAILABLE` | Reservation slot no longer has capacity |
| 409 | `HAS_ACTIVE_ORDERS` | Account deletion while an order is in progress or a reservation is upcoming |
| 403 | `MFA_REQUIRED` | Staff login for a role that needs a second factor (`MANAGER`, `ADMIN`; ADR-0009) |
| 409 | `ORDER_NOT_EDITABLE` | Adding items to an order that is paid or final (`COMPLETED`, `CANCELLED`, `REJECTED`) (brief A8) |
| 409 | `INVALID_STATE` | A change the record's current state does not allow, outside the order and reservation flows: resetting the password of an `INVITED` account, resending an invitation that was already used (brief E7, E10), switching off a voucher that someone else just switched off (W14C decision), issuing an invoice for an order that is not `COMPLETED` (brief N6) |
| 409 | `MFA_NOT_ENABLED` | MFA reset on a user who has no second factor enrolled (staff, or a manager or admin who never enrolled) (brief E9) |
| 409 | `REVIEW_NOT_PUBLISHED` | Replying to, or reporting, a review that is hidden or removed; also a customer editing or deleting their own review that is hidden or removed; proposal, the alternative is to accept and queue it (brief V4, V20; mobile G81, G85, G90) |
| 409 | `DUPLICATE_REPORT` | A second open report by the same customer on the same review (mobile G89) |
| 409 | `IDEMPOTENCY_CONFLICT` | The same `Idempotency-Key` sent with a different body; name and status are a proposal, `422` is the alternative (mobile G57) |
| 409 | `DUPLICATE_RESERVATION` | A customer books an overlapping time at the same branch with a different key; proposal, the alternative is to accept it (mobile G125) |
| 413 | `TOO_LARGE` | Upload over 10 MB (brief B16) |
| 415 | `UNSUPPORTED_TYPE` | Upload of a file type that is not an accepted image (brief B16) |
| 500 | `INTERNAL_ERROR` | Unexpected server error, stable so the console can tell "server error" from "network lost" (brief F9) |

**Payloads added to existing codes** (problem+json members):

- `STALE_VERSION`: `current { rowVersion, updatedBy, updatedAt }` and, for a settings key, the current `value`; for a report decision, who handled it and when (brief B1, C10, L1, V15).
- `IN_USE`: `usage { count, sample[{ id, name }], filter }` so the dialog shows the count, a few names and a filtered link without another call; whether soft-deleted items count is open (brief B26). Table delete or switch-off: `reservations[{ id, reservedAt, durationMinutes, partySize, status, contactName }]` (brief P15). Also used for category delete (B25), tag group change with items (B30), zone delete with orders (C22) and reducing seats or switching off a table with unfinished reservations (W14B decision).
- `HAS_ACTIVE_ORDERS`: also refuses `DELETE /admin/branches/{id}` while orders are in progress or reservations upcoming (brief C1).
- `SLOT_UNAVAILABLE` on a staff confirm: `conflicts[{ tableId, reservationId, from, to }]` (brief P2).
- `UPGRADE_REQUIRED`: carries the store URL of the caller's platform (brief L12).
- `NOT_FOUND`: also the answer for downloading an export file that has expired and was deleted; the screen offers `Tạo lại` (brief J7; `410` is the alternative, see Open items).
- `RATE_LIMITED`: also for a resend within 60 s and a third concurrent export (brief E10, J6).
- `BRANCH_CLOSED`: `reason` (`CLOSED` \| `PAUSED` \| `PAST_CUTOFF` \| `SERVICE_OFF`) and `nextOpenAt` (null when unknown), so the button text and the dialog can differ (mobile G43; the value names are mine).
- `ITEM_UNAVAILABLE`: `items[{ id, soldOut, left? }]`, `id` being the menu item id and `left` present only when stock is tracked and lower than the quantity asked (mobile G56).
- `PRICE_CHANGED`: the body is the fresh quote with its full `lines[]`, so the app compares it with the cart on the device (mobile G55).
- `OPTION_INVALID`: `invalid[{ itemIndex, optionIds[] }]` so the edit sheet can name the options (mobile G34; the brief shows one object, a list is needed when several lines are wrong).
- `ORDER_NOT_REVIEWABLE`: `details { reason }` with `NOT_COMPLETED`, `WINDOW_EXPIRED` or `NOT_OWNER`, so the app picks the right sentence (mobile G87; the value names are mine).
- `HAS_ACTIVE_ORDERS` on `DELETE /me`: `details { orders, reservations }`, the counts that caused the refusal (mobile G112).

**Field-level codes** (`errors[].code` inside `VALIDATION_FAILED`; `errors[].field` is the full path, for example `ordering.board_thresholds.accept.warn`):

| Code | Used for |
|---|---|
| `REQUIRED`, `TOO_LONG`, `OUT_OF_RANGE`, `INVALID_PHONE`, `INVALID_EMAIL`, `INVALID_TAX_CODE`, `MUST_BE_LESS_THAN_LATE`, `MUST_EXCEED_ACCEPT_LATE` | Settings fields (brief L2); `TOO_LONG` also for photo `alt` text and note lengths (brief C32, V17) and, in the customer app, for `items[].note` (200, `ordering.itemNoteMax`), `deliveryNote` (200), `displayName` (60) and a reservation `note` (200) (mobile G32, G46, G95, G129) |
| `RANGE_TOO_WIDE`, `RANGE_INVALID` | Date range of a list, report or export above its limit or inverted (brief A34, J15) |
| `INVALID_CURSOR` | Malformed or expired cursor (400); the screen returns to page 1 (brief H4) |
| `TOO_MANY` | More than 8 photos on an item (`field: media`) (brief B15) |
| `LIMIT_REACHED` | More than 12 photos on a branch (brief C32) |
| `STOCK_NEGATIVE` | A stock `delta` that would take the quantity below 0 (`field: delta`) (brief B36) |
| `MIN_GT_MAX`, `DEFAULT_REQUIRED`, `DEFAULT_EXCEEDS_MAX`, `NOT_ENOUGH_ACTIVE` | Option group rules (brief B9) |
| `LOCKED` | Changing a branch `code` once an order exists, or a voucher `code` after its first redemption (brief C6, M5) |
| `OVERLAP`, `EQUAL_TIMES`, `INVALID_TIME` | `PUT .../hours`: shifts or special ranges that overlap, equal open and close times, malformed time (brief C14, C15) |
| `RADIUS_ORDER` | A delivery ring that breaks the order of rings (brief C19) |
| `LAST_ACTIVE_ZONE` | Turning off or deleting the last active zone of a branch that accepts delivery (brief C21) |
| `TOO_MANY_ROWS` | Export that would exceed the row limit (brief J6) |
| `OUTSIDE_OPENING_HOURS`, `TOO_SOON`, `TOO_FAR`, `PARTY_TOO_LARGE` | `POST /reservations`: the time is outside the reservation hours, sooner than the minimum lead time, further than the days allowed, or the party is larger than the branch accepts; `errors[].field` is `reservedAt` or `partySize` (mobile G124; the brief wrote `details[{ field, reason }]`, the existing `errors[]` shape is used instead) |

## Authentication, customer transport (tokens in the body)

Unchanged from v2 (ADR-0003, ADR-0008 #1, #6): `POST /auth/register` (with `acceptedDocumentIds[]`; `phone` optional at registration, required at first order), `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/logout-all`, `/auth/social/nonce`, `/auth/social/google`, `/auth/social/apple`, `/auth/email/send-code`, `/auth/email/verify`, `/auth/password/forgot`, `/auth/password/reset`. Customer login rejects staff accounts, so the `FORBIDDEN` of an order from a non-customer account cannot come from the customer app (mobile G58).

## Authentication, staff transport (HttpOnly refresh cookie)

`POST /admin/auth/login`, `/admin/auth/refresh`, `/admin/auth/logout`, `/admin/auth/password/forgot`, `/admin/auth/password/set` (invitation and reset links) as in v2. **Accepted** (ADR-0009 risk 1): login returns `MFA_REQUIRED` for `MANAGER` and `ADMIN`, then `POST /admin/auth/mfa/verify` with the TOTP code or one recovery code (single use); `POST /me/mfa/setup`, `/me/mfa/confirm`, `/me/mfa/recovery-codes`.

Rules added from the admin web design (brief, all proposals unless noted):

- A wrong password and a wrong TOTP code both add to `users.failed_login_count`; the lock message hides the unlock time, the attempts left and whether password or code caused it (brief E15). `ACCOUNT_SUSPENDED` is returned only after a correct password (W02A decision).
- Recovery codes: ten single-use codes shown once; the console warns at three left and requires a new set when none are left; `/me/mfa/recovery-codes` issues the set (brief E20).
- An expired or used invitation or reset link returns `CODE_INVALID`, the same as a wrong code (brief E19).
- Login audit events: success and failure, second-step request, code success and failure, temporary lock, password set, logout, refresh-token reuse; never a password, code, token or TOTP secret, and an unknown email typed is not logged. Event names are proposals (brief E17).
- Maintenance never blocks `/admin/auth/*` (brief E18, L13).
- Silent refresh in the admin web: one refresh at a time, shared by all waiting requests; a failed refresh returns to login and the unsent form stays in memory; a `TOKEN_EXPIRED` is retried once, any other `401` goes to login (brief Z9).
- `POST /admin/auth/step-up` `{ code }` (`admin`): returns a short-lived token that must accompany the `PUT` of the `payment` settings key; the last 5 digits of the account number are audited and the other admins are emailed. A wrong code returns `CODE_INVALID`. Proposal; if the owner declines, the code field of the confirm dialog goes away (brief L14).

## Realtime ([ADR-0007](adr/0007-realtime-sync.md))

Connect, event shape, no replay and token handling are as in v2 and ADR-0008 #7 to #12. The audience model changes: an event is scoped to **a branch's staff** or to **one customer**, so a branch never sees another branch's orders.

| Event | Caused by | Audience | Client effect |
|---|---|---|---|
| `order.placed` | Customer app | Staff of the order's branch | New order on the live board with a sound and badge; count in the sidebar |
| `order.status_changed` | Staff | The order's customer; staff of the branch | Customer timeline updates; other staff see who acted; board moves the card. **New staff-side concern: the board must not depend on realtime alone.** A staff tablet that loses its connection shows the connection state prominently and refetches on reconnect and at a short interval while the order board is open, because a missed order is lost revenue (ADR-0009 risk 4). Customers' in-app status relies on realtime and refetch on resume (WA3). The connection counts as lost after 30 seconds (two cycles) with no data, in the customer app as well as on the staff board (mobile G117), and `Cập nhật lúc` is the last data received, by event or refetch (brief I4, I5). The dashboard has no dedicated event (brief F10). There is no banner, points or voucher event: the customer app reloads when the Home, points or wallet screen opens (brief M24; `voucher.updated` is open, M11); it also reloads them when its own order becomes `COMPLETED` or is cancelled (mobile G140). No separate event tells other customers about a new review; the new aggregate arrives inside `branch.updated` (mobile G118).
